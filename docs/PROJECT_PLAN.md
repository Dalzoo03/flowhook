# FlowHook 프로젝트 기획서

버전: 0.2 · 작성일: 2026-09-30 · 상태: 검토용 최종 초안 · 구현 상태: 미착수

읽는 순서: **이 기획서 → [PRD](PRD.md) → [기능 명세서](FUNCTIONAL_SPEC.md)**

세 문서는 한 묶음이다. 기획서는 추진 이유와 범위, PRD는 사용자와 제품 요구사항, 기능 명세서는 정확한 동작과 인수조건을 담당한다. 구현 일정은 [프로젝트 로드맵](FLOWHOOK_PROJECT_ROADMAP.md), 개인별 공부는 [학습 로드맵](BACKEND_LEARNING_ROADMAP.md)을 참고한다.

## 1. 제안과 판단

**FlowHook은 애플리케이션 이벤트를 외부 서버에 전달하고, 실패한 전달의 재시도·조회·복구를 제공하는 개발자용 웹훅 서비스다.**

백엔드 포트폴리오와 기술 학습이라는 목적에는 추천한다. 외부 통신, 데이터 무결성, 동시성, 장애 복구, 배포를 한 사용자 흐름에서 경험할 수 있기 때문이다. 단, 실제 사용 수요와 상용 서비스 차별성은 검증되지 않았다.

제품 유형의 독창성은 낮다. [Svix](https://www.svix.com/)와 [Hookdeck](https://hookdeck.com/docs)은 웹훅 전달·관리 관련 기능을 제공한다. 작은 서비스에는 직접 만든 재시도 코드나 DB 대기열이 충분할 수 있다. FlowHook 도입은 별도 서버·인증·운영 의존성을 추가한다.

프로젝트의 포트폴리오 가치는 직접 재현한 실패와 설계 근거에 달려 있다. 단순 POST 전달과 기술 이름 나열에 그치면 약하다. 복잡한 주문·재고 같은 비즈니스 규칙을 다루는 경험도 이 프로젝트가 모두 대신하지는 않는다.

**추진 조건:** V1을 웹훅 전달과 복구로 한정하고, 실행 가능한 데모와 문제 해결 보고서 2개 이상을 만든다. 범용 workflow는 이후 확장으로 둔다.

## 2. 개발 배경

개발자는 Java 중급 학습을 마쳤고 고급 과정과 Spring 핵심 원리를 공부하고 있다. SQLD를 보유했지만 실제 SQL 경험은 적다. Docker와 간단한 CI/CD 경험이 있고 Kubernetes에도 관심이 있다.

주 3일을 투자해 2027년 1학기 인턴을 준비한다. 따라서 기능 완성과 기술 이해를 함께 확인하고, 강의·코딩테스트·지원 준비를 포함한 일정으로 진행한다.

## 3. 해결할 문제와 대표 상황

주문 서비스가 주문 생성 사실을 파트너 서버 두 곳에 전달해야 한다. 한 곳이 느리거나 실패하면 개발자는 전달 상태 저장, 재시도, 중복 방지, 복구 도구를 직접 마련해야 한다.

FlowHook은 접수한 이벤트를 저장한 다음 각 목적지로 전달하고 그 과정을 보여준다. 개발자는 실패한 목적지만 찾아 복구할 수 있다.

접수 이전의 이벤트 유실은 소스 애플리케이션의 책임 범위다. 후속 학습에서 outbox로 이 경계를 실험한다. 주문 시스템 전체는 만들지 않고 이벤트 발행용 작은 예제를 사용한다.

## 4. 목표와 산출물

| 목표 | 산출물 | 판단 기준 |
|---|---|---|
| 사용할 수 있는 전달 기능 | API·관리 콘솔·데모 수신 서버 | 접수부터 전달 결과 조회까지 시연 |
| 실패 처리 이해 | 재시도·중복·복구 시나리오 | [인수조건](FUNCTIONAL_SPEC.md)의 결과와 일치 |
| DB·Spring 실무 경험 | 모델·쿼리·트랜잭션 설계 기록 | 주요 SQL과 상태 변경을 직접 설명·수정 |
| 운영 경험 | CI·Docker·제한된 데모 배포·기본 지표 | 다른 환경에서 문서로 재현 |
| 여러 기술의 학습 | Redis·Kafka·Kubernetes 비교 실험 | 목적·결과·한계·채택 여부 기록 |
| 인턴 지원 준비 | README·3~5분 데모·보고서 2개 이상 | 실제 구현과 측정한 결과만 기재 |

## 5. 개발 범위

| 구분 | 포함 범위 | 완료 의미 |
|---|---|---|
| M0 로컬 데모 | 한 프로젝트·한 수신 URL·접수·전달·이력 | 전체 흐름을 이해할 수 있는 중간 결과 |
| M1 신뢰성 핵심 | DB 비동기 처리·재시도·중복 접수·수동 재처리·복구 | 주요 장애 동작을 검증한 결과 |
| M2 지원용 V1 | 프로젝트 접근 제어·키·서명·화면·제한 배포·보고서 | 첫 포트폴리오 제출 가능한 범위 |
| 실험 | 다중 worker·Redis·Kafka·Kubernetes | 제품 채택 여부와 관계없이 학습 결과 확보 |
| 후속 제품 | 조건·지연 workflow, 버전·실행 이력, 시각적 편집기 | 인턴 준비 상황에 따라 별도 계획 |

M0·M1은 개발 중간 결과이며 공개 서비스 출시를 의미하지 않는다. 다중 worker의 기본 경쟁·복구 확인은 V1에 포함하고, 확장성 튜닝은 후속 실험에 둔다.

V1 범위에는 공개 회원가입, 조직 초대, 결제·과금, 임의 코드 실행, 범용 payload 변환, 수백 개 SaaS connector, 대형 실시간 대시보드를 포함하지 않는다.

## 6. 예상 일정과 조절 규칙

| 기간 | 목표 |
|---|---|
| 1~4주 | Spring·HTTP 적용, API·검증·첫 CI |
| 5~8주 | SQL·JPA 적용, 저장·전달·이력, M0 |
| 9~12주 | 비동기·재시도·멱등성·기본 복구, M1 |
| 13~14주 | 접근 제어·화면·배포·검증 정리, M2 목표 |
| 15~19주 | Redis·Kafka 실험과 지원 병행 |
| 20~24주 | 선택 Kubernetes 실습, 일정 완충, 면접 준비 |

주 3일, 하루 순수 집중 4~6시간을 임시 가정한다. 12~14주는 낙관적인 목표치다. 4주마다 진행 속도를 확인하고, 지연 시 후속 실험 시간을 V1에 배분한다. 인증·서명·기본 화면은 후반에 한꺼번에 시작하지 않고 각 기능 개발 중 점진적으로 붙인다.

일정이 부족하면 workflow·추가 통계 화면·Kafka의 제품 통합부터 줄인다. 데이터 무결성·권한·복구 설명·지원 준비는 유지한다. 인턴 공고는 지금부터 확인하며 모든 실험 완료를 기다리지 않는다.

## 7. 주요 위험과 대응

| 위험 | 징후 | 대응 |
|---|---|---|
| 범위 증가 | 첫 전달 데모 이전에 엔진·편집기 설계가 늘어남 | M0를 먼저 완료 |
| 이해 없이 구현만 증가 | 주요 SQL·상태 전이를 설명하지 못함 | 작은 예제로 재현 후 진행 |
| 사용 가치가 추상적 | 화면만으로 필요성을 이해하기 어려움 | 파트너 장애와 복구의 전후 데모 |
| 기술 수집으로 변질 | 도구마다 해결 질문이 없음 | 기술별 질문 하나와 종료 기준 설정 |
| 일정 초과 | 8주차에도 저장·전달 흐름이 미완성 | UI 축소, 실험 일정 후순위 조정 |
| 잘못된 신뢰성 주장 | 재전송과 부작용 중복 방지를 혼동 | 수신자 멱등성과 실패 경계를 함께 문서화 |

## 8. 제품 검증과 학습 방식

먼저 합성 데이터와 소유한 수신 서버로 시연한다. 이후 외부 연동 경험이 있는 개발자 2~3명에게 실패 조회와 복구 흐름을 보여주고 직접 구현하는 방식보다 무엇이 편한지 의견을 받는 것을 제안한다. 이는 아직 수행하지 않은 검증 계획이다.

각 기술 실험은 질문 → 기준선 → 변경 → 같은 조건의 관찰 → 한계 → 채택 판단 순서로 기록한다. 실제 개선이 없으면 그 결과도 남긴다.

## 9. 문서 작성 도구와 변경 관리

[BMAD PRD 템플릿](references/bmad/prd-template.md)의 제품 목적·사용자 여정·요구사항 연결 구조와 [GitHub Spec Kit 템플릿](references/spec-kit/spec-template.md)의 우선순위·Given/When/Then 인수조건을 적용했다. 실제 적용 범위와 소스 버전은 [도구 검토 기록](TOOLING_REVIEW.md)에 있다.

요구사항은 PRD의 FR/NFR ID, 상세 규칙은 기능 명세서의 POL ID, 확인 기준은 AC ID로 연결한다. 앞으로 정책이 바뀌면 관련 ID와 인수조건을 같이 수정한다. 문서 상태는 최종 초안이며 사용자 확정·구현 완료·성능 검증을 의미하지 않는다.
