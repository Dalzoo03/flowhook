# FlowHook PRD — 제품 요구사항 정의서

버전: 0.2 · 작성일: 2026-09-30 · 상태: 검토용 최종 초안 · 구현 전

[기획서](PROJECT_PLAN.md) · [기능 명세서](FUNCTIONAL_SPEC.md) · [도구 적용 기록](TOOLING_REVIEW.md)

## 1. 목적과 제품 정의

FlowHook은 애플리케이션 이벤트를 접수해 설정된 외부 서버로 전달하고, 실패 이력 조회와 복구를 지원한다. 본 문서는 제품이 제공해야 할 가치와 동작을 정의하며 내부 클래스 구조와 기술 선택은 구현 로드맵·후속 설계에서 다룬다.

개발 목적은 2027년 1학기 인턴을 위한 백엔드 포트폴리오와 실무 기술 학습이다. 제품 가치 가설은 외부 연동 실패의 확인·재시도·복구 부담을 줄이는 것이다. 실제 고객 수요는 미검증이다.

## 2. 사용자와 해야 하는 일

- **주 사용자:** 외부 연동을 개발·운영하는 백엔드 개발자. 수신 URL과 이벤트 유형을 설정하고, 실패를 확인하고 복구한다.
- **API 이용자:** 개발자가 만든 소스 애플리케이션. 프로젝트 API 키로 이벤트를 접수한다.
- **데모 평가자:** 실행 안내와 콘솔을 이용해 정상·실패·복구 동작을 확인한다.

V1에서 일반 소비자용 자동화, 사무 업무용 no-code, 팀별 복잡한 권한 관리는 대상에 포함하지 않는다.

## 3. 용어

| 용어 | 정의와 관계 |
|---|---|
| 프로젝트 | 한 소유자의 이벤트·수신 URL·키를 묶는 단위 |
| 이벤트 | eventId·type·data로 표현한 소스 애플리케이션의 사실 |
| 수신 URL(endpoint) | 이벤트 유형 하나를 구독하는 목적지 설정 |
| 전달(delivery) | 이벤트 하나를 수신 URL 하나에 보내는 논리 작업 |
| 시도(attempt) | 한 delivery의 전송 시도와 결과 기록 |
| 자동 재시도 | 정책에 따른 후속 전송 |
| 수동 재처리(replay) | 최종 실패한 delivery를 새 처리 회차로 다시 실행 |
| 처리 회차 | 최초 전달 또는 한 번의 수동 재처리부터 시작하는 시도 묶음 |

하나의 이벤트는 여러 delivery를 가질 수 있고 하나의 delivery는 여러 attempt와 처리 회차를 가질 수 있다. 회차가 바뀌어도 delivery의 식별자는 유지한다.

## 4. 사용자 여정과 우선순위

P1은 핵심 전달 가치, P2는 운영·복구 가치다. 아래 UJ-01~04는 모두 V1에 포함한다. 독립 확인은 공통 프로젝트·인증 환경과 필요한 초기 데이터가 준비됐다는 전제에서 수행하며, 실제 개발 의존성을 없다는 뜻으로 해석하지 않는다.

### UJ-01 · P1 · 이벤트를 전달하고 결과 확인

개발자는 로그인 후 프로젝트와 키를 만들고 수신 URL·유형을 등록한다. 소스 애플리케이션에서 이벤트를 접수한 뒤 콘솔에서 해당 이벤트와 delivery를 확인한다. 수신 서버의 성공 응답이 표시되면 첫 연동이 끝난다.

독립 확인: 정상 수신 서버 하나에 이벤트를 보내 접수·수신·이력 조회를 확인한다. 관련 FR-001~008, FR-011~012.

### UJ-02 · P1 · 외부 장애의 자동 복구 확인

기존 연동의 수신 서버가 일시적으로 실패한다. 개발자는 콘솔에서 실패 시도와 다음 예정 시각을 확인한다. 수신 서버가 복구되면 자동 재시도가 성공하고 이전 실패 이력도 남는다.

독립 확인: 두 번 실패한 뒤 성공하는 수신 서버로 자동 복구를 확인한다. 관련 FR-009~010, FR-012, FR-017, FR-019.

### UJ-03 · P2 · 최종 실패한 전달 수동 복구

개발자는 최종 실패 필터로 delivery를 찾아 상세에서 원인과 고정된 목적지를 확인한다. 외부 원인을 해결한 뒤 재처리한다. 새 처리 회차의 진행 상황과 이전 시도를 함께 확인한다.

독립 확인: 미리 만든 최종 실패 데이터에서 재처리와 중복 클릭의 결과를 확인한다. 관련 FR-011~015.

### UJ-04 · P2 · 안전하게 연동 운영

개발자는 키를 폐기하거나 수신 URL을 중지·수정한다. 변경이 신규 이벤트와 기존 delivery에 각각 어떻게 적용되는지 확인한다. 서비스가 재시작돼도 기존 이력을 조회하고 남은 작업을 이어간다.

독립 확인: 두 사용자와 대기 데이터로 권한·설정 변경·재시작 동작을 확인한다. 관련 FR-001~005, FR-016~019.

## 7. 범위와 화면

V1: 프로젝트·키, 수신 URL 설정, 이벤트·전달 이력, 서명·재시도·재처리, 프로세스 재시작 복구, 최소 인증, 제한된 데모 배포.

후속: 조직 권한, 공개 회원가입, payload 변환, workflow와 편집기, 대형 통계, 실시간 갱신, 사용자별 retry 정책, 일반 외부 URL 공개 지원.

화면은 로그인 / 프로젝트·키 설정 / 수신 URL 목록·설정 / 이벤트 목록·상세 / 전달 목록 / 전달 상세로 구성한다. 빈 목록, 대상 없음, 권한 없음, 요청 실패, 중지 때문에 대기 중인 상태도 표시한다. delivery 상세는 현재 endpoint URL과 실제 고정된 전달 URL이 다를 때 이를 분명하게 구분한다.

균형 지표: 접수 속도를 높여도 유실·대기 증가·실패율을 숨기지 않는다. 재시도 횟수를 줄인 것만으로 효율 개선이라고 평가하지 않는다. 접수 성공과 외부 처리 성공은 별도 지표다.

## 10. 보장 범위

접수는 저장 완료를 의미한다. 외부 HTTP 2xx는 수신 서버의 비즈니스 작업 완료를 증명하지 않는다. 재전송은 가능하며 수신자가 delivery ID로 중복 부작용을 막아야 한다. 재시도 한도와 영구 장애 때문에 최종 성공을 약속하지 않는다. V1은 엄격한 도착 순서를 보장하지 않는다.

URL 수정은 기존 delivery의 대상을 바꾸지 않는다. 잘못된 과거 URL을 새로운 URL로 강제 재전송하는 기능은 후속이다. endpoint 중지는 이미 전송을 시작한 요청을 취소하지 못할 수 있다.

## 12. 변경 이력과 문서 연결

0.1에서 0.2로 사용자 여정, FR/NFR ID, 인수조건 연결, 초기 정책, 가정·미결정 항목을 추가했다. 제품 추진 판단은 기획서, 정확한 수치·상태·오류 동작은 기능 명세서가 담당한다. 정책 변경 시 FR·AC·POL 간 연결을 함께 갱신한다.
