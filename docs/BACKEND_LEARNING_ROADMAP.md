# 개인 백엔드 학습 로드맵

작성일: 2026-09-30 · 목표: 2027년 1학기 인턴 지원 준비 · 기준 프로젝트: FlowHook

구현할 제품의 상세는 [FlowHook 프로젝트 로드맵](FLOWHOOK_PROJECT_ROADMAP.md)에 있다. 이 문서는 무엇을 언제 배우고, 어디에 적용하고, 어느 수준에서 다음 단계로 넘어갈지를 정리한다.

## 1. 출발점과 목표

사용자가 직접 알려준 현재 상태:

- Java: 김영한 중급 과정을 충분히 익혔고 고급 과정 수강 중.
- Spring: 입문 수강 완료, 핵심 원리 기본편 진행 중.
- SQL: SQLD 보유, 실제 쿼리 작성·운영 경험은 적음.
- Docker와 간단한 CI/CD 경험이 있으며, Kubernetes에도 관심이 있음.
- 주 3일 집중 가능. 내년 4학년 1학기, 즉 2027년 1학기 인턴이 목표.
- 포트폴리오 완성과 여러 기술을 사용하며 배우는 것 모두 중요함.

Java 입문을 반복하는 일정은 잡지 않는다. 앞으로 시간을 가장 많이 쓸 곳은 Spring 요청 처리, 실제 SQL, 트랜잭션, 장애 처리다. Java 고급은 이 작업에 필요한 동시성·I/O 중심으로 이어간다.

인턴 준비 목표는 기능을 설명하고 수정할 수 있는 서버, 재현 가능한 실험 2~3개, 기본 SQL·CS·코딩테스트, 그리고 지원 자료다. 인턴 합격은 회사별 채용 상황과 평가에 따라 달라지므로 특정 기술이나 프로젝트 규모로 보장하지 않는다.

## 2. 공부와 프로젝트를 함께 진행하는 방식

한 주제마다 아래 순서를 사용한다.

1. 필요한 개념을 강의와 문서로 배운다.
2. 작은 예제를 자료를 덮고 다시 만든다.
3. 같은 개념을 FlowHook의 기능 하나에 적용한다.
4. 잘못된 입력·실패·동시 요청 중 하나를 넣어 본다.
5. 왜 그렇게 동작하는지 설명하고 짧게 기록한다.

강의 완강은 이해를 확인하는 수단 중 하나다. 전체 Spring·JPA 과정을 끝내기 전에 프로젝트의 작은 부분을 시작한다. 반대로 이해하지 못한 동시성·트랜잭션 코드를 대량으로 받아 구현 진도만 앞당기지 않는다.

여러 기술은 충분히 써본다. 다만 기본 제품과 비교 실험의 결과를 구별한다. 예를 들어 Redis는 전송량 제한 실험, Kafka는 독립 소비자와 재처리 실험, Kubernetes는 배포·복구 실험으로 각각 질문을 하나씩 잡는다.

## 3. 주 3일의 운영 예시

하루 순수 집중 4~6시간, 주 12~18시간을 임시 기준으로 둔다. 이 시간에는 강의, 프로젝트, 코딩테스트, 기록이 모두 포함된다. 주 3일을 모두 8시간 작업으로 가정하지 않는다.

| 날 | 기본 배분 | 남길 것 |
|---|---|---|
| 첫째 날 | 개념·강의 2시간, 적용 2~3시간, 코테 1시간 | 작은 동작과 이해 질문 |
| 둘째 날 | 구현 2~3시간, SQL·CS 1시간, 코테 1시간 | 기능 한 조각과 직접 쓴 쿼리 |
| 셋째 날 | 구현·실험 2~3시간, 문서·복습 1시간, 코테 또는 지원 준비 1시간 | 실패 재현 결과와 다음 작업 |

주 12시간만 가능하면 각 날의 구현 범위를 줄인다. 시험 주간에는 새 기능을 줄이고 작은 복습·코테와 진행 중 작업 정리로 전환한다. 학교 OS·네트워크·DB 과목은 관련 실습과 연결하되, 과제 시간을 이 일정에 중복 계산하지 않는다.

초기 6주는 강의와 실습 비중이 높고, 이후에는 구현과 실험 비중을 높인다. 코테·지원 준비를 프로젝트가 끝날 때까지 미루지 않는다. 기존 iOS 활동은 일정 안에서 유지할 수 있지만 새로운 대형 프로젝트를 동시에 시작하는 것은 피한다.

## 5. 첫 12주 실행 계획

이 표는 매주 강의를 한 편씩 완강한다는 뜻이 아니다. 해당 주제의 필요한 범위를 배우고 적용한다. 밀리는 경우 뒤의 선택 실험 기간을 사용한다.

| 주 | 배울 내용 | FlowHook에서 할 일 | 넘어갈 기준 |
|---|---|---|---|
| 1 | 핵심 원리: 객체 역할, DI, 구성 | endpoint 등록 유스케이스를 작은 객체로 설계 | 구현체 교체가 어디에 영향을 주는지 설명 |
| 2 | Bean, 생성자 주입, Java 예외·테스트 | 메모리 저장소와 검증, 첫 CI | Spring 없이도 주요 규칙을 테스트 |
| 3 | HTTP 메서드·상태·헤더·JSON·timeout | API 요청·응답 초안, 로컬 receiver | 이벤트 접수와 전달 성공을 구분 |
| 4 | MVC 요청 처리, DTO, validation, 오류 응답 | endpoint·event HTTP API | 정상·잘못된 입력을 직접 요청하고 설명 |
| 5 | SELECT/JOIN/GROUP BY, 키·제약 | 스키마 초안, 직접 SQL로 데이터 조회 | ORM 없이 전달 이력을 조회 |
| 6 | DB1의 JDBC·커넥션·트랜잭션 | PostgreSQL 저장, 마이그레이션 | 두 저장 중 실패하면 무엇이 남는지 재현 |
| 7 | JPA 기본, 영속성, 변경 감지, 조회 | event/delivery/attempt 저장 모델 | 실제 생성 SQL과 트랜잭션 경계 설명 |
| 8 | HTTP client, 서명, Docker, 최소 UI | 한 번 전달하고 결과 조회, 이미지 빌드 | 200·500·timeout·서명 검증을 시연 |
| 9 | 비동기와 영속 상태, Java executor | DB 대기열과 단일 worker, 접수 응답 분리 | 요청이 끝난 뒤에도 작업이 DB에 남음 |
| 10 | retry/backoff, 시간 모델링 | 재시도·최종 실패 상태, 기본 지표 | 실패 유형별 정책과 재시도 시각 설명 |
| 11 | unique constraint, 멱등성, 접근 제어 | 중복 접수, 수동 재처리, 프로젝트 권한 | 중복·충돌·권한 없음의 결과 구분 |
| 12 | 배포·설정·관측·장애 재현 | 제한된 데모 배포, 복구 기본 실험, README | 실행·실패·복구 흐름을 3~5분 시연 |

접근 제어·송신 대상 제한·비밀 관리가 준비되지 않았으면 12주의 데모는 로컬 또는 접근이 제한된 환경에서 진행한다. 공개 주소를 만드는 것만으로 배포 단계가 끝나는 것은 아니다.

13~14주는 미완료 작업을 정리하고 두 worker 경쟁, lease 복구, 성능 기준선을 확인하는 완충 구간이다. 여기까지가 첫 포트폴리오 완성 범위다.

## 6. 과목별로 어느 깊이까지 공부할지

### Java — 이미 아는 내용은 적용으로 확인

계속 볼 것: 불변 객체, equals/hashCode, 예외 분류, 제네릭, 컬렉션, 시간 타입. 고급 과정에서는 스레드 안전성, executor, lock, interrupt·종료, blocking I/O를 우선 연결한다.

FlowHook 적용: 공유 카운터의 경쟁, 제한된 worker 수, timeout, 종료 신호 처리, 재시도 시간 계산. JVM은 heap·stack·GC와 간단한 thread dump부터 익힌다. virtual thread나 CompletableFuture 비교는 기본 worker가 동작한 뒤 작은 실험으로 해도 된다.

확인 질문:

- 스레드를 늘리면 항상 처리량이 늘어나는가?
- 작업이 DB 커넥션을 기다리는 것과 HTTP 응답을 기다리는 것은 어떻게 다른가?
- 동시에 수정되는 상태와 불변 데이터의 차이는 무엇인가?
- 프로세스가 종료되면 메모리에만 있던 작업은 어떻게 되는가?

### Spring — 현재 강의 다음에 바로 작은 API로 연결

기본편 → HTTP → MVC의 요청·응답 처리 → 검증·예외·인증 기초 → DB 접근과 트랜잭션 순으로 진행한다. 이후 필요한 시점에 AOP와 Boot 설정·운영 기능을 깊게 본다.

기존에 따르는 [김영한 공식 Spring 로드맵](https://www.inflearn.com/roadmaps/373)의 큰 순서를 존중하되, FlowHook 적용에 필요한 부분을 먼저 복습한다. MVC의 서버 템플릿·국제화·파일 업로드를 모두 숙련한 뒤 REST API를 시작할 필요는 없다. DB2의 여러 접근 기술은 비교 목적을 이해하고 이 프로젝트에서는 JPA에 집중한다.

`@Transactional`은 애너테이션 이름을 외우는 수준에서 멈추지 않는다. 같은 객체 내부 호출과 프록시 경유 호출의 차이를 작은 코드로 확인한다. 기본 프록시 모드에서는 내부 호출에 새로운 트랜잭션 advice가 적용되지 않는다. [Spring 공식 트랜잭션 문서](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)

확인 질문:

- HTTP 요청은 어떤 단계를 거쳐 controller에 도달하는가?
- controller와 service 각각에서 무엇을 책임지는가?
- 외부 HTTP 호출을 DB 트랜잭션 안에 넣으면 어떤 문제가 생기는가?
- 세션, 프로젝트 API 키, JWT는 이 프로젝트에서 각각 어떤 선택지인가?

### SQL·PostgreSQL — 가장 먼저 늘려야 할 실무 경험

SQLD에서 익힌 용어를 실제 쿼리와 데이터로 확인한다. 매주 SQL 시간을 확보한다.

1. 프로젝트별 이벤트 수와 endpoint별 실패 수를 직접 조회한다.
2. JOIN, GROUP BY, 서브쿼리로 전달 상세·실패 목록을 만든다.
3. PK/FK/NOT NULL/UNIQUE와 마이그레이션을 적용한다.
4. 두 세션에서 같은 데이터를 수정해 격리와 잠금을 관찰한다.
5. 1만 건에서 시작해 10만 건으로 늘리고 EXPLAIN ANALYZE를 비교한다.
6. 상태·다음 처리 시각을 조건으로 조회하는 쿼리의 인덱스를 설계한다.
7. 데이터가 충분히 쌓인 뒤 cursor pagination과 보관 정책을 검토한다.

복합 인덱스는 필드 이름만 보고 고정하지 않고 실제 WHERE·ORDER BY·데이터 분포로 결정한다. 다른 DB의 clustered index 설명을 PostgreSQL에 그대로 대입하지 않는다. 사용 중인 DB에서 관찰한 동작을 기준으로 정리한다.

확인 질문:

- 애플리케이션의 중복 조회만으로 경쟁 요청의 중복 저장을 막을 수 있는가?
- 이 인덱스가 이 쿼리에 도움이 되는 근거는 무엇인가?
- 인덱스가 늘어나면 쓰기와 저장 공간에는 어떤 영향이 있는가?
- 트랜잭션이 실패했을 때 API는 어떤 결과를 반환해야 하는가?

### JPA — SQL을 볼 수 있을 때 깊게

핵심은 영속성 컨텍스트, 변경 감지, 연관관계, 지연 로딩, N+1, fetch 전략, pagination, 트랜잭션이다. 실제 조회 화면에 문제가 생기면 SQL 수와 실행계획으로 확인한다.

도메인마다 무조건 양방향 연관관계를 만들지 않는다. worker 선점처럼 DB 기능이 중요한 부분은 명시적 SQL도 비교한다. Querydsl, 복잡한 상속 매핑, 모든 cascade 옵션을 처음부터 완료 목록으로 넣지 않는다.

완료 기준: 조회 하나의 SQL과 필요한 인덱스를 설명하고, 변경 저장·롤백·지연 로딩의 동작을 작은 사례로 재현할 수 있다.

### 신뢰성·동시성 — FlowHook의 핵심 학습

접수 중복, 전달 중복, 재처리 중복을 구별한다. 멱등성은 어떤 작업을 어떤 키와 기간으로 중복 판정하는지까지 정해야 한다.

DB 선점, lease, 소유 토큰, 복구 시각을 공부하고 두 worker로 실험한다. 작업을 선점한 뒤 외부 호출이 성공했지만 DB 기록이 실패하는 경우를 다룬다. 이때 외부 서버가 실제로 무엇을 했는지 모를 수 있다는 점을 설명해야 한다.

완료 기준: at-least-once 전달과 수신자 멱등 처리의 관계, timeout 이후의 불확실성, DB 트랜잭션만으로 외부 HTTP를 되돌릴 수 없는 이유를 설명한다.

### Docker·CI/CD·운영 — 초반부터 반복

Docker는 image/container, network, volume, 환경 설정, 종료 신호를 익힌다. DB 데이터를 남기는 volume과 컨테이너 수명 차이를 직접 확인한다.

CI는 첫 주제부터 빌드·검증을 자동화한다. DB 통합 테스트가 생기면 CI에도 연결한다. 이미지가 생기면 tag와 재현 가능한 빌드를 정리하고, 배포 가능 버전부터 CD를 붙인다.

초기 배포는 익숙한 단일 VM과 Compose 정도로 시작할 수 있다. AWS를 쓰면 IAM·보안 그룹·TLS·로그·DB 데이터 보존을 필요한 범위부터 이해한다. RDS·ALB·다중 서버는 후속 비교 대상이다. 자동 배포 전에 설정과 마이그레이션 실패, 이전 이미지로 복귀하는 절차를 익힌다. 앱 rollback이 DB 스키마 변경까지 자동으로 되돌리는 것은 아니다.

Linux는 프로세스, 포트, 파일 권한, 로그, CPU·메모리, signal을 실행 중인 서버에 연결해서 배운다. 컨테이너를 재시작했을 때 무엇이 남고 사라지는지 말할 수 있어야 한다.

### 관측·부하 실험 — 결과를 읽는 능력

처음부터 request/event/delivery 식별자와 실행 시간을 남긴다. 기본 Actuator·Micrometer 지표를 이해하고, 부하를 비교하기 전에 Prometheus·Grafana를 작은 범위로 붙인다. OpenTelemetry tracing은 API·worker·외부 요청 연결이 필요해질 때 확장한다.

로그에는 개별 ID를 남길 수 있지만, 지표 label에 무제한 event ID나 delivery ID를 넣는 방식은 피한다. 성공률·재시도·queue age·DB 커넥션·JVM을 먼저 본다.

완료 기준: “느리다”를 접수 지연, 대기 지연, 외부 서버 지연으로 나눠 설명하고, 변경 전후 동일 조건에서 측정할 수 있다.

### Redis·Kafka·Kubernetes — 각각 작은 완료 기준

| 기술 | 시작 전 조건 | 첫 실험 | 완료 기준 |
|---|---|---|---|
| Redis | worker와 실패 처리가 동작 | worker 두 개의 전송량 제한 | 원자성·TTL·장애 정책 설명 |
| Kafka | DB 비동기 전달과 중복 처리 이해 | 두 consumer group, 중복 소비, outbox | offset·partition·중복·DB 경계 설명 |
| Kubernetes | Docker 배포와 상태 확인·종료 처리 이해 | 배포, replica, Pod 종료, update·rollback | 각 리소스 역할과 복구 동작 설명 |

각 실험은 1~3주 단위로 제한한다. 새 도구의 모든 기능을 배우는 목표로 확장하지 않는다. Redis 자료형 전체, Kafka 운영 전체, Kubernetes 관리자 수준을 인턴 전 필수 범위로 묶지 않는다.

Redis의 카운터와 만료는 [공식 예제](https://redis.io/docs/latest/commands/incr/), Kafka의 처리 보장 범위는 [공식 설계 문서](https://kafka.apache.org/41/design/design/), Kubernetes는 [공식 기초 실습](https://kubernetes.io/docs/tutorials/kubernetes-basics/)에서 확인하며 진행한다.

## 7. 코딩테스트·CS·면접 준비

코테 언어는 익숙한 Java를 유지한다. 시작 기준은 주 3회, 회당 40~60분이다. 처음에는 배열·문자열·해시·스택·큐·정렬을 확인하고 BFS/DFS, 이분 탐색, heap, greedy, 기본 DP 순으로 빈 곳을 채운다. 이미 해결 가능한 유형은 빠르게 넘어간다.

문제 수보다 다시 풀 수 있는지가 중요하다. 풀지 못한 문제는 풀이를 본 뒤 며칠 후 다시 풀고 시간·공간 복잡도와 선택 이유를 말한다. 8주차 이후에는 지원 기업 유형에 맞춰 시간을 제한한 연습을 추가한다. 현재 코테 실력은 확인되지 않았으므로 난이도 목표는 첫 2주 결과로 조정한다.

CS는 매주 프로젝트 질문 하나와 연결한다.

| 과목 | 프로젝트에서 확인할 질문 |
|---|---|
| 네트워크 | DNS부터 HTTP 응답까지 무슨 일이 일어나며 timeout은 어느 단계인가? |
| 운영체제 | 스레드가 기다릴 때 CPU·메모리·커넥션은 어떻게 사용되는가? |
| DB | 격리·잠금·인덱스가 중복 접수와 worker 처리에 어떤 영향을 주는가? |
| 자료구조 | 자료 크기에 따라 조회·정렬·대기 작업 관리 비용이 어떻게 달라지는가? |
| 보안 | 인증과 권한 검사는 어떻게 다르며 webhook URL 입력에 어떤 위험이 있는가? |

면접 답변은 정의 → 내 코드의 사례 → 관찰한 결과 → 한계 순서로 2분 내 설명해 본다. 모르는 결과를 기술 이름으로 덮지 않는다.

## 8. 지원 자료는 이렇게 쌓는다

1~4주: 기존 프로젝트와 역할, 내가 직접 해결한 문제를 이력서 초안에 적는다. 관심 공고에서 필수 요건과 우대 요건을 구분한다.

5~8주: FlowHook의 실제 동작 범위, API와 데이터 모델, 실행 방법을 README에 정리한다. 미구현 기능을 구현한 것처럼 표시하지 않는다.

9~14주: 실패 재현 보고서 2~3개와 데모를 만든다. 인턴 공고가 열리면 완료된 결과를 바탕으로 지원한다.

15주 이후: Redis·Kafka 등 실험이 끝날 때마다 결과를 업데이트한다. 지원 기업에서 기본 SQL·Spring·코테 준비가 더 급하면 확장 실험을 줄인다.

첫 제출용 저장소에는 다음이 있으면 좋다.

- 어떤 문제를 해결하는지 보여주는 짧은 설명과 시연.
- 실행 방법, 구성도, 핵심 API, 사용한 버전.
- 실패·중복·재시작 복구 사례와 재현 절차.
- 실제 측정 조건과 수치가 있는 보고서.
- 설계 대안과 선택 이유, 아직 보장하지 못하는 동작.
- 빌드·검증·배포 절차와 내가 직접 맡은 범위.

## 9. 도움을 받으면서 실력을 남기는 방법

코드 초안이나 설명의 도움을 받더라도 핵심 판단은 직접 확인한다. 특히 상태 전이, 트랜잭션 범위, SQL, retry, 동시성은 코드를 읽고 설명할 수 있어야 한다.

한 번에 요청하는 작업을 한 유스케이스 또는 한 실패 조건으로 줄인다. 변경 내용을 읽고 예상 동작을 적은 다음 직접 요청·DB 결과·로그를 확인한다. 이해가 안 되는 부분은 그 코드를 줄인 작은 예제로 다시 실습한다.

매주 하나는 도움 없이 수정해 본다. 예를 들어 “429는 Retry-After를 반영하게 바꾸기” 또는 “전달 목록에 실패 상태 필터 추가하기”처럼 작은 요구가 적절하다. 직접 수정할 수 없는 기능이 계속 쌓이면 구현 속도를 낮추고 이해를 보완한다.

## 10. 진행 점검과 범위 조절

2주마다 세 가지를 확인한다: 동작하는 결과가 생겼는가, 내가 설명·수정할 수 있는가, 실패를 한 번이라도 재현했는가.

| 시점 | 확인할 결과 | 부족하면 할 일 |
|---|---|---|
| 4주 | API와 오류 응답을 직접 만들고 설명 | 새로운 도구를 줄이고 MVC 적용 반복 |
| 8주 | PostgreSQL 저장과 전달 상세 조회 | 프론트 범위 축소, SQL·트랜잭션 보완 |
| 12~14주 | 재시도·복구·접근 제어·데모·보고서 | Redis·Kafka 시작을 미루고 V1 마무리 |
| 18~20주 | 적어도 한 기술 비교 실험, 지원 자료 | 두 번째 실험 또는 Kubernetes를 줄임 |
| 22~24주 | 설명 가능한 포트폴리오와 면접 준비 | 새 기능보다 지원·면접에서 드러난 빈 곳 보완 |

가장 먼저 줄일 것은 범용 workflow와 시각적 편집기다. 그다음 Kubernetes 확장, Kafka의 서비스 통합 순서로 조절한다. 기본 API·SQL·트랜잭션·실패 처리와 지원 준비는 유지한다.

## 11. 다음 세 번의 집중일

첫째 날: 핵심 원리 수강을 이어가며 endpoint 등록을 객체 몇 개로 설계한다. 입력·출력·검증 규칙을 적고, 생성자 주입이 바꾸는 점을 설명한다.

둘째 날: 메모리 저장소로 등록·조회 API를 만들고 정상·잘못된 입력을 요청한다. 작은 테스트와 빌드 CI를 연결한다.

셋째 날: PostgreSQL에서 project·endpoint 테이블을 직접 생성하는 실습을 하고 INSERT·SELECT·JOIN을 작성한다. 아직 JPA로 감싸기 전에 실제 데이터와 쿼리를 확인한다. 이번 주 이해한 것과 다음 주 HTTP에서 확인할 질문을 적는다.
