# FlowHook 프로젝트 로드맵

작성일: 2026-09-30 · 상태: 구현 전 제안 · 목표: 2027년 1학기 인턴 지원에 활용할 백엔드 포트폴리오

제품 목적과 범위: [프로젝트 기획서](PROJECT_PLAN.md) · 제품 요구사항: [PRD](PRD.md) · 기능별 동작과 완료 기준: [기능 명세서](FUNCTIONAL_SPEC.md)

2026-09-30 문서 정리: 제품 문서는 v0.2로 개정했다. 이 로드맵은 구현·학습 순서를 유지하며, V1의 구체적인 동작·초기 정책은 PRD와 기능 명세서를 우선한다.

이 문서는 기존 `flowhook-codex-handoff.zip`의 계획을 검토하고, 기술 학습 목적과 현재 학습 수준을 반영해 제안한 수정안이다. 구현 완료를 뜻하지 않는다. 개인별 공부 순서와 첫 12주 계획은 [백엔드 학습 로드맵](BACKEND_LEARNING_ROADMAP.md)에 있다.

## 1. 프로젝트에 대한 판단

FlowHook은 계속 진행할 만한 주제다. 외부 HTTP 요청, 데이터 저장, 실패 복구, 동시성, 운영을 하나의 흐름에서 경험할 수 있다. 특히 정상 동작뿐 아니라 실패를 재현하고 수정한 과정을 보여주기 좋다.

다만 프로젝트의 범위는 조절해야 한다. 웹훅 전송 서비스와 범용 워크플로 엔진은 각각 상당한 작업이다. 첫 포트폴리오 완성점을 웹훅 서비스로 잡고, 워크플로는 이후 확장으로 둔다. 새로운 종류의 제품이라는 주장이나 실제 고객 수요가 검증됐다는 주장은 하지 않는다. 대표 데모와 기술적 근거를 먼저 만든다.

제품 정의:

> 애플리케이션의 이벤트를 받아 등록된 외부 서버에 전달하고, 실패한 전달을 재시도·조회·복구할 수 있는 개발자용 서비스.

대표 사용자: 외부 연동 실패 때문에 재시도 코드와 복구 스크립트를 반복해서 만드는 백엔드 개발자.

대표 시나리오: 주문 서비스에서 `order.created` 이벤트 발생 → FlowHook 접수 → 파트너 서버 전달 → 파트너 장애 → 재시도 → 실패 이력 확인 → 파트너 복구 후 재처리.

## 2. 기존 계획에서 바꾸는 점

| 기존 방향 | 수정 제안 | 이유 |
|---|---|---|
| 문제가 측정됐을 때만 Redis·Kafka 도입 | 제품 채택과 학습 실험을 구분 | 학습 자체도 유효한 목적이다. 실험 후 채택하지 않아도 결과가 남는다. |
| 비동기 처리·복구를 뒤 단계에 배치 | 첫 학습용 전달 후, V1 완성 전 DB 기반 비동기 처리 도입 | 접수 후 응답과 실제 전달을 분리한다는 제품 설명에 맞춘다. |
| 관측 도구를 Phase 6에 일괄 도입 | 초반에 추적 ID·시간·오류 기록, 부하 비교 전에 지표 도입 | 개선 전 기준선이 있어야 비교할 수 있다. |
| 배포·CI/CD를 후반에 도입 | 첫 API부터 CI, 최소 기능 뒤 Docker 배포, 이후 CD·복구 | 운영 경험을 반복해서 쌓는다. |
| 워크플로를 중간 필수 단계로 배치 | 인턴 지원용 V1 이후 선택 확장 | 엔진과 편집기 때문에 서비스 완성이 지연되는 것을 막는다. |
| 조직·사용자·프로젝트부터 넓게 모델링 | 초기에는 사용자 소유 프로젝트와 프로젝트별 API 키 | 팀 초대·역할 관리까지 시작 범위에 넣으면 인증 제품에 시간이 쏠린다. |
| 외부 서버를 추상적인 대상으로 취급 | 장애를 조절하는 데모 수신 서버 추가 | 실패 실험과 포트폴리오 시연을 재현할 수 있다. |
| 소스 애플리케이션에서 이벤트가 도착한다고 가정 | 이벤트 발행 전 유실 가능성을 설명하고 후속 outbox 실습 추가 | FlowHook이 접수하지 못한 이벤트까지 복구할 수는 없다. |

기본 원칙은 유지한다. 하나의 Spring Boot 애플리케이션과 PostgreSQL로 시작하고, 역할에 따라 패키지를 나눈다. 서비스 분리와 추가 인프라는 실험 결과와 운영 부담까지 비교해 결정한다.

## 3. 완성점과 우선순위

### A — 기본 동작 데모: 약 6~8주

endpoint 등록 → 이벤트 접수 → HTTP 전달 → 시도 결과 조회. 로컬에서 전체 흐름을 보여준다. 이 단계의 제한도 문서화한다.

### B — 인턴 지원용 V1: 약 12~14주

DB 기반 비동기 전달, 재시도, 중복 접수 처리, 실패 조회·재처리, 서명, 재시작 복구, 최소 인증, 제한된 데모 배포를 갖춘다. 작업자 2개에 대한 경쟁 실험과 재현 가능한 기술 보고서 2~3개를 목표로 한다. 시간이 부족하면 다중 작업자 심화 실험을 V1 직후에 마무리한다.

### C — 기술 확장 실험: 약 15~20주

Redis로 여러 작업자 사이의 전송량 제한을 실험하고, Kafka로 이벤트 분배와 중복 소비를 실험한다. 두 실험을 모두 운영 서비스에 통합하는 것은 필수 조건이 아니다. 느려지거나 복잡해진 결과도 기록한다.

### D — 선택 확장: 약 21주 이후

로컬 Kubernetes 운영 실습 또는 작은 워크플로 엔진 중 하나를 먼저 선택한다. 현재 관심과 인턴 일정 기준으로는 Kubernetes를 짧게 실습하고 워크플로는 후순위로 두는 안을 추천한다.

기간은 주 3일, 하루 순수 집중 4~6시간을 가정한 계획치다. 강의·코딩테스트·기록을 포함한다. 실제 집중 시간이 더 적거나 DB·트랜잭션 이해가 지연되면 C·D를 줄이고 B를 완성한다.

## 4. 추천 저장소와 초기 구성

```text
flowhook/
  backend/                  # Spring Boot 애플리케이션 하나
  console/                  # 최소 Next.js 관리 화면, API가 생긴 뒤 추가
  demo/
    receiver/               # 정상·오류·지연 응답 및 중복 수신 확인
    producer/               # 처음에는 이벤트 전송 스크립트
  infra/
    compose/                # PostgreSQL → 앱 → 선택 도구 순으로 확장
  experiments/              # Redis·Kafka·Kubernetes 비교 실험
  docs/
    adr/                    # 실제로 결정한 설계와 근거
    experiments/            # 조건·재현 절차·결과·해석
```

백엔드는 `projects`, `events`, `endpoints`, `deliveries`, `auth` 정도의 기능별 패키지로 시작한다. 각 기능이 커질 때 필요한 controller/service/repository를 둔다. 초기부터 별도 Gradle 모듈, 범용 실행 엔진, 공통 BaseService를 만들 필요는 없다.

초기 기술: Java 21을 기준 후보로 한 지원 중 JDK, Spring Boot, Spring MVC, JPA, PostgreSQL, Gradle, Flyway, JUnit, 필요한 곳의 Testcontainers. 구체적인 버전 조합은 프로젝트 생성 시 공식 호환 범위를 확인하고 고정한다. 강의 예제의 의존성을 그대로 복사하지 않는다.

프론트의 첫 범위는 endpoint 목록, 이벤트 목록, 전달 상세다. 이후 실패 필터와 재처리 버튼을 추가한다. 백엔드 접근 규칙과 이벤트 처리 로직은 Spring에 모은다.

## 5. 단계별 구현 계획

### P0. 골격과 학습용 실습 — 1~3주

- 프로젝트 용어와 대표 시나리오를 한 페이지로 정리한다.
- Spring 애플리케이션, 간단한 상태 확인 API, PostgreSQL 실행 구성을 만든다.
- 생성자 주입과 테스트 가능한 객체 설계를 endpoint 등록 유스케이스에 적용한다.
- Java의 시간 타입, 예외, 컬렉션을 실제 모델에 적용한다.
- GitHub 저장소를 마련한 뒤 첫 빌드·단위 테스트 CI를 연결한다.

완료 기준: 실행 절차가 재현되고, 잘못된 입력을 거절하며, CI에서 빌드 실패를 확인할 수 있다. CI 연결 시 저장소·권한 등 실제 외부 작업은 그 시점의 설정 범위에 따라 진행한다.

### P1. 전달 한 번을 끝까지 구현 — 4~8주

- endpoint와 이벤트의 HTTP API, 요청 검증, 공통 오류 응답을 만든다.
- 초반에는 메모리 저장소로 요청 흐름을 익히고, DB 학습과 함께 PostgreSQL로 교체한다.
- event, delivery, attempt를 구분해 저장한다.
- 데모 수신 서버에서 200·500·지연 응답을 선택한다.
- HTTP 연결/응답 시간 제한과 응답 본문 저장 크기 제한을 둔다.
- 발신 payload 서명을 만들고 데모 수신 서버에서 검증한다.
- 이벤트 ID, 전달 ID, 시도 번호, 소요 시간, 실패 분류를 기록한다.

초기 동기 전달은 로컬에서 실패와 지연을 배우는 짧은 실습으로 사용한다. 외부 HTTP 호출을 DB 트랜잭션 안에 넣지 않는다. 이 실습을 최종 비동기 제품의 완료 상태로 표시하지 않는다.

완료 기준: 정상·500·timeout을 서로 구별해서 조회하고, 네트워크 오류가 언제 발생했는지 설명한다. DB 마이그레이션으로 빈 DB를 구성할 수 있다.

### P2. 신뢰성 있는 비동기 전달 — 9~12주

- 이벤트와 전달 대기 행을 하나의 DB 트랜잭션으로 저장한다.
- 저장이 커밋된 뒤 접수 응답을 반환한다. 응답은 전달 성공을 뜻하지 않는다.
- worker가 DB의 실행 가능한 delivery를 가져와 외부 HTTP 요청을 보낸다.
- 대기 시각을 DB에 기록하고 재시도 때 그 시각을 조회한다. 장시간 sleep으로 작업 스레드를 붙잡지 않는다.
- 지수형 backoff, jitter, 최대 시도 횟수, 최종 실패 상태를 구현한다.
- 프로젝트와 외부 이벤트 ID의 유일 제약으로 동시 중복 접수를 처리한다.
- 실패 건의 수동 재처리와 재처리 요청 이력을 추가한다.
- 최소 인증과 프로젝트별 접근 제한을 붙인다.
- 제한된 대상만 호출하는 데모 배포, 구조화 로그, 기본 운영 지표를 만든다.

권장 정책 초안: 2xx 성공, 네트워크 오류·timeout·429·5xx 재시도, 대부분의 다른 4xx 최종 실패. 408 등 예외는 정책으로 명시한다. 429의 Retry-After는 최대 대기 범위를 두고 반영한다. 자동 redirect는 기본적으로 끈다. 초기에는 사용자별 복잡한 재시도 편집 UI 없이 정책을 고정한다.

완료 기준: 수신 서버를 잠깐 중단해도 접수된 이벤트가 남고, 복구 후 정해진 정책에 따라 다시 처리된다. 중복 접수가 추가 논리 delivery를 만들지 않으며, 최종 실패 건을 찾아 재처리할 수 있다.

### P3. 작업자 경쟁·복구·지원용 정리 — 13~14주

- worker 2개로 같은 대기 목록을 처리한다.
- 작업 선점과 제한된 처리 권한 시간(lease)을 저장한다.
- 작업자가 죽으면 만료된 작업을 회수한다.
- 이전 작업자가 늦게 돌아와 새 결과를 덮어쓰지 못하도록 소유 토큰 또는 버전을 검사한다.
- 수신 성공 직후 결과 저장 전에 프로세스를 종료하는 실험을 한다.
- DB 조회 실행계획, 전달 지연, 커넥션 사용을 관찰한다.
- 재현 보고서, README, 3~5분 시연, 알려진 한계를 정리한다.

`SKIP LOCKED`는 큐 성격의 행을 여러 소비자가 가져가는 데 활용할 수 있다. 선점할 때 짧게 잠근 뒤 커밋하고, HTTP 호출은 트랜잭션 밖에서 수행한다. lease 만료 후에는 오래된 worker와 새 worker가 모두 외부 요청을 보낼 가능성이 있으므로 DB 선점만으로 외부 부작용의 단일 실행을 약속하지 않는다. [PostgreSQL 잠금 문서](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE)

완료 기준: 일반 경쟁과 장애 복구를 구분해 설명하고, 복구되지 않는 작업이나 영구 PROCESSING 상태가 발생하는 경로를 점검한다. 외부 HTTP 중복 가능성을 데모 수신자의 멱등 처리와 함께 설명한다.

### P4. Redis 비교 실험 — 15~16주

질문: worker가 여러 개일 때 endpoint별 초당 전송량을 어떻게 함께 제한할까?

- 단일 프로세스 메모리 제한의 동작을 먼저 확인한다.
- worker를 두 개로 늘려 각자 카운트하면 전체 제한을 초과하는 상황을 재현한다.
- Redis의 카운터·만료·원자적 연산을 이용한 제한을 비교한다.
- 제한 초과 시 delivery를 삭제하지 않고 다음 처리 시각으로 미룬다.
- Redis가 중단됐을 때 전달을 잠시 멈출지 제한적으로 허용할지 정한다.
- 제한 정확도, 추가 지연, 실패 상황, 운영 부담을 기록한다.

첫 구현은 fixed window로 시작할 수 있지만 경계 순간의 burst 한계를 명시한다. 시간이 있으면 token bucket 등과 비교한다. 카운터 증가와 만료 설정을 나누면 중간 실패로 만료 없는 키가 남을 수 있으므로 원자성도 검토한다. [Redis 카운터·rate limiter 예제](https://redis.io/docs/latest/commands/incr/)

완료 기준: Redis의 역할과 장애 시 정책을 설명하고, 서비스 채택 또는 실험 종료를 결정한다. 캐시와 분산 락을 동시에 추가하지 않는다.

### P5. Kafka와 이벤트 발행 경계 실험 — 17~19주

질문: 전달 처리와 집계가 같은 이벤트를 독립적으로 소비하게 하려면 무엇이 달라질까?

- topic, partition, consumer group, offset을 작은 producer/consumer 실습으로 익힌다.
- 전달용 소비자와 간단한 집계용 소비자를 분리한다.
- 소비자 중단·재시작, offset commit 전후 실패, 중복 소비를 재현한다.
- DB 저장과 메시지 발행 중 한쪽만 성공하는 문제를 만들고 outbox로 비교한다.
- 같은 부하 조건에서 DB 기반 처리와 지연·복구·운영 복잡도를 비교한다.
- Kafka를 채택할지, 학습용 실험으로 남길지 ADR에 기록한다.

범위는 producer → outbox → Kafka → 두 소비자 정도로 제한한다. Kafka가 자동으로 외부 HTTP의 exactly-once 부작용을 보장하지 않는다. Kafka 내부 읽기·처리·쓰기 보장과 외부 시스템 호출을 구분한다. [Apache Kafka 전달 의미](https://kafka.apache.org/41/design/design/)

예약 시각이 있는 재시도는 우선 PostgreSQL 스케줄링을 유지한다. Kafka를 넣는다는 이유로 모든 delivery 상태와 예약을 브로커로 옮기지 않는다.

소스 이벤트 발행 실습은 별도 범위다. 데모 주문 저장과 outbox 저장을 하나의 트랜잭션으로 묶고, relay가 FlowHook에 이벤트를 재전송하게 한다. 이것은 FlowHook 접수 이후의 복구와 다른 경계다. Kafka 실험 시간이 부족하면 이 작은 HTTP outbox 실습을 먼저 완료해도 된다.

### P6. Kubernetes 운영 실습 — 20~21주, 선택

- 기존 Docker 이미지를 로컬 kind 또는 minikube에 배포한다.
- Pod, Deployment, Service, 설정 주입을 이해한다.
- readiness/liveness를 구분하고 DB 장애 시 무조건 재시작시키는 설계를 피한다.
- Pod 삭제 후 복구, worker 2개, rolling update, rollback을 실험한다.
- 종료 신호를 받았을 때 신규 선점 중단과 진행 중 작업 처리를 설명한다.
- Docker Compose 배포와 비교해 얻은 점과 추가 부담을 기록한다.

여기서는 API·worker 운영에 집중한다. PostgreSQL·Kafka까지 직접 운영하는 클러스터, Helm 생태계, service mesh, EKS는 추가 목표로 잡지 않는다. K8s 학습용 Secret에 실제 키를 커밋하지 않는다. [Kubernetes 공식 기초 실습](https://kubernetes.io/docs/tutorials/kubernetes-basics/)

완료 기준: YAML을 복사하는 수준을 넘어 배포·스케일·복구를 실행하고 어떤 리소스가 어떤 역할을 했는지 설명한다.

### P7. 작은 워크플로 — 인턴 준비 이후 선택

이벤트 → 조건 → webhook → 지연 후 webhook 정도의 고정된 실행 모델로 시작한다. 조건은 허용된 필드·연산자만 사용한다. 사용자 임의 코드 실행을 넣지 않는다.

버전이 고정된 정의, 실행 상태, 노드별 기록, 재시작 후 이어하기를 구현한다. 첫 버전은 순차 실행과 단순 분기만 지원하고 병렬 합류·루프는 뒤로 둔다. React Flow 편집기는 실행 엔진이 검증된 뒤 붙인다. 이 단계의 완료 여부가 V1 포트폴리오 제출을 막지 않게 한다.

## 6. V1의 데이터와 API 초안

구현 중 ADR로 확정할 제안이다. UI보다 데이터의 책임과 상태 전이를 먼저 맞춘다.

| 모델 | 책임 | 핵심 제약·참고 |
|---|---|---|
| User | 콘솔 사용자 | 조직·팀 초대는 이후 |
| Project | 이벤트와 endpoint의 소유 경계 | 모든 조회·변경에서 접근 권한 검사 |
| ApiKey | 외부 애플리케이션의 이벤트 접수 인증 | 원문 재노출 없이 해시 저장, 폐기 가능 |
| WebhookEndpoint | URL, 활성 상태, 이벤트 유형 구독, 서명키 참조 | V1은 구독 유형 한 개부터 시작 가능 |
| ApplicationEvent | 접수한 불변 이벤트 | `(project_id, external_event_id)` 유일 |
| Delivery | 이벤트를 특정 endpoint로 보내는 논리 작업 | `(event_id, endpoint_id)` 유일 |
| DeliveryAttempt | 실제 HTTP 시도와 결과 | `(delivery_id, attempt_no)` 유일, 시간·오류·상태 기록 |
| ReplayRequest | 수동 재처리 요청과 사유 | 요청 키 중복 방지, 요청자·시각 기록 |

event와 delivery는 처음에는 같은 DB 트랜잭션으로 생성한다. 이벤트 유형과 대상 endpoint의 매칭 기준 시점은 접수 시점으로 고정한다. V1에서는 구독 변경이 기존 delivery의 대상을 바꾸지 않는다.

| API | 의도 |
|---|---|
| `POST /api/projects` | 콘솔 사용자의 프로젝트 생성 |
| `POST /api/projects/{id}/endpoints` | webhook 대상 등록 |
| `GET /api/projects/{id}/endpoints` | 대상 조회 |
| `POST /v1/events` | API 키에 연결된 프로젝트로 이벤트 접수 |
| `GET /api/projects/{id}/events` | 접수 이력 조회 |
| `GET /api/projects/{id}/deliveries?status=...` | 전달 이력 조회 |
| `GET /api/projects/{id}/deliveries/{deliveryId}` | 전달 및 시도 상세 |
| `POST /api/projects/{id}/deliveries/{deliveryId}/replays` | 실패 건 재처리 요청 |

인증 API와 키 관리 API의 상세는 인증 방식 결정 뒤 추가한다. 콘솔은 세션 인증을 기본 후보로 비교하고, 이벤트 접수는 프로젝트 API 키로 나눈다. 쿠키 인증에서는 CSRF, 교차 출처 요청에서는 CORS·쿠키 정책을 함께 다룬다. JWT가 꼭 필요한지를 먼저 확인한다.

## 7. 코딩 전에 고를 중요한 규칙

1. **접수 멱등성:** 동일 프로젝트와 이벤트 ID로 같은 내용이 들어오면 기존 접수 결과를 반환한다. 내용이 다르면 충돌로 거절한다. 내용 비교를 위한 정규화·해시 기준과 보관 기간을 정한다.
2. **전달 멱등성:** 동일 delivery의 retry/replay에는 안정적인 delivery ID를 전달한다. 수신자가 그 ID로 중복 부작용을 억제하는 데모를 만든다. 수신자의 중복 판정 보관 기간도 replay 가능 기간과 맞춘다.
3. **재처리:** V1은 최종 실패 상태에서만 허용한다. 새 replay 요청을 기록하고 동일 논리 delivery를 다시 대기로 바꾼다. 과거 attempt는 보존한다. 누적 attempt 번호와 재처리 회차별 재시도 횟수를 구분한다. 경쟁 요청은 트랜잭션과 상태 조건으로 직렬화한다.
4. **순서:** V1은 전역 순서나 endpoint별 엄격한 도착 순서를 보장하지 않는다. 재시도가 순서를 바꿀 수 있음을 API 설명과 데모에 적는다.
5. **대상 변경:** 이미 생성된 delivery가 사용할 URL·payload를 고정하고, endpoint 변경은 새 delivery부터 적용하는 방안을 기본으로 한다. 보안상 endpoint 비활성화는 기존 대기 작업에도 적용한다. 서명키 교체는 버전과 전환 정책을 정한다.
6. **보관:** payload·응답 본문·오류 기록의 크기와 보관 기간을 제한한다. 비밀키와 인증 헤더를 로그에 남기지 않는다. outbound 서명키는 서명에 사용할 수 있게 보호해 보관해야 하므로 API 키처럼 해시만 저장하는 방식과 구분한다.
7. **수용 범위:** 대상이 없는 이벤트는 접수하되 delivery가 0개임을 보여주는 방안을 기본으로 한다. 이벤트 크기, 한 이벤트당 대상 수, 대기열 한도를 정한다. 한도 초과는 명시적으로 거절한다.

상태 초안은 `PENDING → PROCESSING → SUCCEEDED / RETRY_WAIT / DEAD`다. 프로세스가 죽어 결과를 모르는 attempt는 불명확한 결과로 기록할 수 있어야 한다. `DEAD`는 초기에는 DB 상태로 충분하며 별도 메시지 큐 제품을 뜻하지 않는다.

## 8. 공개 데모 전 필요한 보호

FlowHook은 사용자가 지정한 URL로 서버가 요청을 보내는 구조다. 따라서 내부 주소·클라우드 메타데이터 등으로 호출이 향하지 않도록 SSRF 방어가 필요하다. 초기 공개 데모는 소유한 수신 서버만 허용하는 allowlist 방식이 단순하다. 임의 외부 URL 지원은 DNS 해석, redirect, 실제 연결 대상, 송신 네트워크 제한까지 함께 검토한 다음 넓힌다. 개발용 로컬 receiver 허용은 개발 환경에만 둔다. [OWASP SSRF 방어 지침](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)

서명은 body 원본 바이트와 timestamp 등을 합의한 형식으로 검증하고, 수신 측 시간 허용 범위와 중복 처리를 함께 구현한다. 서명 검증만으로 replay가 방지되는 것은 아니다. 프로젝트 간 조회 차단, 요청·응답 크기 제한, 외부 호출 제한, 비밀 정보 관리도 공개 전에 확인한다.

## 9. 포트폴리오 실험과 증거

| 실험 | 관찰할 내용 | 남길 결과 |
|---|---|---|
| 수신 서버를 느리게 하기 | 접수 응답 시간과 전달 완료 시간의 차이 | 동기 실습과 비동기 버전 비교 |
| 같은 이벤트를 동시에 전송 | event/delivery 개수, 충돌 처리 | DB 유일 제약과 경합 처리 설명 |
| 500·timeout·429 | 재시도 간격과 최종 상태 | 재시도 정책과 타임라인 |
| 처리 중 worker 종료 | 재시작 후 회수 시간, 중복 가능성 | lease 복구와 보장 범위 |
| 수신 성공 후 DB 저장 전 종료 | 외부 부작용과 로컬 상태 불일치 | exactly-once 한계와 수신자 멱등성 |
| worker 1개와 2개 | 처리량, 대기 시간, 충돌 | 확장 효과와 제한 |
| 전달 목록 1만→10만 건 조회 | 실행계획, 응답 시간 | 인덱스 전후 비교 |
| Redis 또는 Kafka 중단 | 계속 가능한 일, 멈추는 일 | 장애 정책과 복구 절차 |

성능 실험은 동일 장비·자원 제한·payload·endpoint 수·수신 서버 지연을 기록한다. 워밍업, 측정 시간, 요청 생성 방식, 반복 횟수도 고정한다. 수신 서버 자체가 병목인지 확인한다.

처리량만 보지 않는다. 접수 지연, 접수부터 전달 완료까지의 시간, queue depth와 가장 오래 대기한 작업의 나이, 실패율, DB 커넥션, JVM/CPU를 함께 본다. 처음부터 특정 RPS 달성을 성과로 약속하지 않는다. 오류를 제외한 성공 요청만으로 지연을 계산했는지도 표시한다.

첫 보고서 목표는 2~3개다. 각 보고서는 문제 → 재현 조건 → 가설 → 대안 → 변경 → 측정 → 한계 순으로 작성한다. `실험 예정`, `실험 완료`, `서비스 채택`을 구분하고 측정하지 않은 숫자는 이력서에 쓰지 않는다.

## 10. 일정이 밀릴 때의 결정

먼저 줄일 것: React Flow, 범용 workflow, Kafka의 본 서비스 통합, Kubernetes 확장, 복잡한 조직 권한 UI.

유지할 것: 데이터 무결성, 실패 이력, 재시도·재처리, 복구 설명, 프로젝트 접근 제한, 재현 가능한 배포와 보고서.

V1이 미완성인데 기술 실험이 늘어나면 다음 실험을 멈추고 V1을 끝낸다. V1이 완성됐다면 새 기술을 직접 써볼 시간도 확보한다. 실험에서 채택하지 않기로 한 근거 역시 학습 결과다.
