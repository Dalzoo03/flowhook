# FlowHook 기능 명세서

버전: 0.2 · 작성일: 2026-09-30 · 상태: 검토용 최종 초안 · 구현 전

[기획서](PROJECT_PLAN.md) · [PRD와 요구사항 목록](PRD.md) · [도구·검토 기록](TOOLING_REVIEW.md)

## 1. 적용 범위와 읽는 방법

이 문서는 PRD의 FR-001~019와 NFR-001~008을 실제 동작으로 풀어 쓴다. 기능 분류 F-01~10은 이전 초안의 번호를 유지한다. `POL`은 기본 정책, `AC`는 사전 조건(Given)·동작(When)·기대 결과(Then)로 작성한 인수조건이다.

모든 수치는 로컬·제한된 데모용 제안값이다. 사용자와 확정되거나 측정된 성능을 의미하지 않는다. 변경할 때는 해당 정책과 AC를 함께 수정한다.

## 2. V1 기본 정책

| ID | 정책 | 기본 제안과 경계 |
|---|---|---|
| POL-01 | 소유권·인증 | 사전 생성 계정, 사용자 소유 프로젝트, 콘솔 세션 인증, 접수 전용 프로젝트 API 키 |
| POL-02 | 이벤트 형식 | eventId와 type은 1~128자 문자열, data는 JSON 객체, 요청 최상위는 이 세 필드만 허용; 중복 JSON 키 거절 |
| POL-03 | 자동 재시도 | 회차당 최초 포함 최대 5시도; 실패 시 기본 대기 5·10·20·40초에 각각 ±20% jitter |
| POL-04 | 호출 시간 | 연결 최대 2초, 응답 대기 최대 5초, 전체 HTTP 시도 최대 10초; 전체 상한을 우선 적용 |
| POL-05 | 처리·복구 | 처리 권한 30초; 만료된 작업을 정상 worker가 15초 내 재시도 대기 또는 한도 종료 상태로 전환하는 것을 데모 목표로 함 |
| POL-06 | 요청·응답 크기 | 접수 body 최대 64 KiB, 시도별 응답 본문 저장 최대 4 KiB; 잘림 표시, 무제한 body 다운로드 금지 |
| POL-07 | 데모 데이터 한도 | 프로젝트당 endpoint 최대 10개, 이벤트 최대 10,000개; 초과 신규 생성 거절, 기존 조회·재처리 유지 |
| POL-08 | 보관·중복 판정 | 합성 데이터 사용, 자동 삭제 없음; 이벤트·delivery·attempt·재처리 키와 결과를 환경 데이터 수명 동안 보관 |
| POL-09 | 대상 고정 | 접수 당시 활성 endpoint만 연결; URL·이벤트 본문·대상 연결을 delivery에 고정; 과거 건 자동 재매칭 없음 |
| POL-10 | 중지 | 신규 이벤트는 중지 endpoint와 미연결; 기존 대기 건은 전송 보류, 이미 시작한 호출은 완료될 수 있음 |
| POL-11 | 재처리 | DEAD이면서 endpoint 활성일 때만 가능; 동일 데이터·delivery ID 유지, 새 회차 생성, 과거 attempt 보존 |
| POL-12 | 재처리 경쟁 | 요청 키와 expectedVersion 필수; 같은 키·같은 입력 재요청은 원래 결과, 같은 키·다른 입력은 충돌 |
| POL-13 | 송신·서명 | 공개 데모는 소유 목적지 허용 목록, redirect 미추적; 서명으로 body·delivery ID·timestamp를 보호, 수신 시간 허용 오차 ±5분 |
| POL-14 | 조회 | 기본 20개, 최대 100개 페이지 조회; 접수 시각과 내부 ID로 안정적인 정렬; 화면에 시간대 표시 |

POL-05는 worker와 DB가 정상 작동하고 여유 처리 자원이 있는 통제된 환경의 확인 목표다. 지속 장애·과부하 중의 복구 SLA가 아니다. lease를 선점 대기열에 쌓아두지 않고 실제 처리 가능량만 선점해야 한다. 전체 호출 상한보다 lease를 길게 두되, 이것만으로 중복 HTTP가 제거된다고 주장하지 않는다.

429의 유효한 Retry-After는 최대 10분까지 반영하고 계산된 backoff보다 이른 재시도를 만들지 않는다. 잘못된 값은 backoff만 사용한다. 최대 시도에 도달하면 추가 예약을 만들지 않는다. 서비스 재시작은 횟수와 예정 시각을 초기화하지 않는다.

데모 한도는 합성 부하 실험에서만 명시적으로 높일 수 있다. 변경 값과 데이터 수를 결과에 기록한다. 환경 초기화 시 보관·중복 판정 이력도 사라진다는 점을 실행 문서에 적는다. 자동 삭제나 운영용 보존 정책은 별도 후속 기능이다.

## 3. 기능별 동작

### F-01. 로그인과 프로젝트 — FR-001,002

사전 생성한 계정으로 로그인·로그아웃한다. 사용자마다 프로젝트를 생성·조회·이름 수정할 수 있다. 공개 회원가입과 영구 삭제 기능은 V1에 없다.

관리 API는 세션 인증과 서버 측 소유권 검사를 사용한다. 인증 없이는 401, 다른 소유자의 자원은 존재를 노출하지 않는 404로 처리한다. 상태 변경 요청은 CSRF 검증을 적용한다. 목록·상세·키 관리·설정·재처리에 같은 규칙을 적용한다.

프로젝트 이름은 1~80자이며 앞뒤 공백을 제거한 뒤 빈 값은 거절한다. UI의 project 선택이 서버 측 권한을 대신하지 않는다.

### F-02. API 키 — FR-003

프로젝트 소유자는 키에 이름을 붙여 생성·목록 조회·폐기한다. 원문은 발급 시 한 번만 보여준다. 이후에는 식별용 일부 값·생성 시각·상태를 표시한다. 원문은 해시로 검증하고 원문 재조회 기능을 제공하지 않는다.

API 키는 이벤트 접수에만 사용할 수 있다. 키로 콘솔 조회나 재처리를 할 수 없다. 폐기 후 신규 요청은 거절하고 기존에 접수한 delivery는 계속 처리한다. 폐기와 정확히 경쟁하는 진행 중 요청은 인증 검사 시점에 이미 허용됐다면 접수될 수 있음을 운영 문서에 명시한다.

### F-03. 수신 URL 설정 — FR-004,005

입력: 이름(1~80자), URL, 구독 이벤트 유형 하나. 유형은 event.type과 대소문자를 포함해 정확 일치한다. 여러 endpoint가 같은 유형을 구독할 수 있다.

URL 형식·허용 목록을 등록과 변경 때 검사한다. 공개 데모에서는 HTTPS의 소유 목적지만 허용하고 개발 환경의 로컬 receiver 예외는 분리한다. 실제 전송에도 허용 정책을 적용한다. URL 중복 등록은 별도 endpoint로 취급하므로 추가 전달이 발생함을 화면에 알린다.

endpoint별 서명키를 생성해 최초 등록 시만 원문을 보여준다. 서명에 사용할 키는 보호된 복구 가능 형태로 보관하고 보호용 비밀은 DB와 분리한다. 상세 알고리즘·헤더·키 버전·비상 교체 절차는 PRD OQ-002에서 확정한다. 키 교체 UI는 후속이다.

수정은 이후 신규 delivery부터 적용한다. 과거 URL·payload를 고정한 기존 delivery를 현재 URL로 암묵적으로 바꾸지 않는다. 상세 화면에 실제 전달 대상과 현재 설정이 다름을 표시한다.

중지 중에는 기존 PENDING/RETRY_WAIT의 신규 전송을 보류한다. 중지 기간에 접수한 이벤트는 해당 endpoint에 소급 연결하지 않는다. 재개하면 기존 대기 작업이 다시 실행 가능해지며 순서 보장은 없다. 이미 시작한 HTTP 요청은 완료될 수 있다.

### F-04. 이벤트 접수 — FR-006,007

키가 지정한 프로젝트에 eventId·type·data를 접수한다. 내부 식별자와 클라이언트의 eventId를 구분한다. 한 이벤트는 접수 시점에 일치하는 활성 endpoint별로 delivery 하나를 갖는다.

신규 이벤트와 전달 작업의 저장이 모두 성공한 뒤 202를 반환한다. 응답에는 내부 ID, 클라이언트 eventId, matchedDeliveryCount, duplicate=false를 포함한다. 저장 실패는 성공으로 응답하지 않는다. 대상이 없으면 접수하되 deliveryCount=0과 대상 없음 상태를 표시한다.

동일 프로젝트와 eventId의 처리:

- type과 data가 같으면 200과 원래 이벤트 정보, duplicate=true를 반환한다. 이후 endpoint 변경으로 delivery를 추가하지 않는다.
- 내용이 다르면 409 EVENT_ID_CONFLICT를 반환한다.
- type은 정확히 비교한다. data의 객체 키 순서는 무시하고 배열 순서·문자열·불리언·null은 구별한다. 숫자는 십진 값으로 비교해 1과 1.0은 같게 취급하고, 이진 부동소수점 변환으로 큰 정수를 뭉개지 않는다. 중복 JSON 키와 비표준 숫자는 거절한다.
- 요청에 projectId 등 정의되지 않은 최상위 필드를 추가하면 400이다. 키의 소유 프로젝트를 변경하지 못한다.

동시 접수도 같은 결과를 가져야 한다. 내용 충돌 판정과 신규 저장의 경쟁을 서버가 제어한다. 용량에 도달했더라도 유효한 동일 이벤트 재요청은 원래 결과를 돌려주고, 신규 이벤트만 한도로 거절한다.

### F-05. 전달과 서명 — FR-008

접수 요청이 끝난 뒤 worker가 실행 가능한 delivery를 처리한다. 외부 요청은 HTTP POST와 JSON을 사용하며 이벤트 ID·유형·데이터를 담는다. 재시도·재처리에 걸쳐 같은 delivery ID를 제공하고 매 시도의 timestamp와 서명을 갱신한다.

외부 HTTP 호출 동안 DB 트랜잭션을 유지하지 않는다. 시작·종료 시각, 소요 시간, 응답 코드, 오류 분류, 제한된 응답 본문을 기록한다. API 키나 인증 헤더는 payload·로그에 포함하지 않는다.

attempt는 서버가 전송을 시작하려고 선점한 시도를 뜻한다. 네트워크 송신 직전 종료되면 실제 수신 요청 없이도 불명확한 attempt가 남을 수 있다. 따라서 attempt 수와 수신 서버의 실제 요청 수가 항상 같다고 가정하지 않는다.

### F-06. 재시도와 최종 실패 — FR-009,010

| 결과 | 상태 변화 |
|---|---|
| 2xx | SUCCEEDED |
| 408·429·5xx·일시 네트워크 오류·timeout | 남은 시도가 있으면 RETRY_WAIT |
| 나머지 4xx·3xx | DEAD |
| URL 정책 위반·서명키 사용 불가 등 영구 설정 오류 | DEAD, 설정 오류 사유 |
| 회차 내 최대 시도 소진 | DEAD |
| 프로세스 종료로 전송 결과 불명 | attempt는 UNKNOWN, 회수 시 남은 시도에 따라 재시도 또는 DEAD |

UNKNOWN도 해당 회차의 소진 시도에 포함해 반복 crash가 무한 재시도가 되지 않게 한다. 다음 시도는 POL-03 정책으로 예약한다. 수신 2xx는 HTTP 전달 성공일 뿐 수신자의 업무 처리 완료를 뜻하지 않는다.

DEAD에는 최종 실패 이유와 종료 시각을 기록하고 nextAttemptAt은 비운다. RETRY_WAIT에만 다음 예정 시각을 표시한다. 이력과 적용 정책은 상세에서 조회할 수 있다.

### F-07. 목록과 상세 — FR-011,012

이벤트 목록: ID, 유형, 접수 시각, 연결된 delivery 수. 전달 목록: 대상, 상태, 마지막 결과, 시도 횟수, 다음 예정 시각. 전달 필터: 상태·endpoint·이벤트 ID.

상세: 고정된 payload와 URL, 현재 endpoint 설정, 처리 회차, 각 attempt의 시각·상태·응답·오류·잘림 여부, 재처리 요청자·시각·사유, 현재 version. 시간이 UTC 저장값이라도 화면에는 표시 시간대를 함께 알린다.

중지에 의한 대기는 별도 사유로 표시한다. 빈 목록·대상 없음·권한 없음·조회 오류를 구분한다. V1은 수동 새로고침을 제공한다. 정책 값은 이 화면에서 확인할 수 있지만 사용자별 편집 기능은 후속이다.

### F-08. 수동 재처리 — FR-013,014,015

입력은 delivery ID, expectedVersion, Idempotency-Key와 선택 사유(최대 500자)다. DEAD·활성 endpoint 조건을 만족하면 같은 delivery를 새 회차의 PENDING으로 전환하고 202와 재처리 요청 ID를 반환한다.

버전은 delivery의 상태 변경 때 증가하는 값이다. 사용자가 확인한 최종 실패 상태와 요청 시점의 상태가 다르면 409 STALE_VERSION이다. 오래 열린 화면의 요청이 다른 처리 회차 종료 후 다시 재처리를 시작하지 않게 한다.

요청 키 범위는 프로젝트+delivery다. 같은 키와 같은 expectedVersion·사유의 재요청은 저장된 최초 결과를 반환한다. 이 조회는 현재 상태 검사보다 먼저 수행한다. 같은 키로 입력이 달라지면 409 REPLAY_KEY_CONFLICT다.

다른 요청 키로 같은 expectedVersion을 동시에 제출하면 하나만 새 회차를 만든다. 나머지는 충돌한다. 성공·진행 중·중지 목적지에는 신규 재처리를 허용하지 않는다. 이미 성공한 동일 요청 키의 조회는 원래 결과를 계속 반환한다.

eventId·delivery ID·payload·고정된 URL은 유지한다. 이전 attempt는 보존하고 누적 번호는 이어가되 새 회차의 시도 예산은 새로 시작한다. 잘못된 과거 URL을 수정된 주소로 보내는 기능은 V1에 없다. 새 이벤트로 재발행하면 새로운 업무 사건으로 처리될 수 있으므로 자동 우회하지 않는다.

### F-09. 재시작과 경쟁 — FR-016,017,018

PENDING/RETRY_WAIT·예정 시각·소진 횟수·이력은 프로세스 재시작을 지나 유지된다. 진행 중 작업은 소유 토큰과 만료 시각으로 관리하고 만료 후 회수한다.

짧은 선점 작업으로 worker 사이의 유효 소유를 제어하고, 결과 저장에도 소유 토큰·버전을 확인한다. 이전 worker의 늦은 응답은 새 worker의 상태를 덮어쓰지 못한다. 만료된 작업자가 외부 요청을 이미 보냈다면 중복 HTTP가 발생할 수 있다.

회수된 불명확한 attempt를 임의로 성공 처리하지 않는다. 회차 시도 한도가 남았으면 재시도하고 없으면 결과 불명과 예산 소진 사유를 기록해 DEAD로 종료한다. 중지 endpoint는 회수 상태 정리만 하고 실제 신규 전송은 재개까지 보류한다.

### F-10. 장애 시연 도구 — FR-019

발행기는 정상 이벤트, 동일 이벤트 반복, 동일 ID의 내용 충돌을 보낼 수 있다. 처음에는 스크립트나 저장된 API 요청 모음이면 충분하다.

수신 서버는 정상, 두 번 실패 후 성공, 지속 500, 지연, 429 모드를 제공한다. 서명을 검증하고 실제 수신 횟수와 업무 반영 횟수를 따로 기록한다. delivery ID와 업무 반영 기록을 영속적으로 함께 저장해 수신자 재시작 후에도 중복 효과를 억제한다. 중복 판정 이력은 데모 환경 데이터 수명 동안 보관한다.

서로 다른 endpoint에서 같은 이벤트가 별개 작업으로 처리되는 것은 정상이다. 중복 판정 단위는 각 목적지의 논리 delivery다. 장애 모드 변경은 로컬 개발용 접근으로 제한한다.

## 4. 상태 전이

| 현재 상태 | 조건 | 다음 상태·처리 |
|---|---|---|
| PENDING | 활성 목적지와 유효 선점 | PROCESSING |
| RETRY_WAIT | 예정 시각 도달·목적지 활성·유효 선점 | PROCESSING |
| PROCESSING | 현재 소유자의 2xx 기록 | SUCCEEDED |
| PROCESSING | 재시도 가능 실패·남은 예산 | RETRY_WAIT |
| PROCESSING | 영구 오류 또는 예산 소진 | DEAD |
| PROCESSING | 소유 만료 | 이전 attempt UNKNOWN, 예산에 따라 RETRY_WAIT 또는 DEAD |
| DEAD | 유효한 신규 재처리 | 새 회차 PENDING |
| SUCCEEDED | 신규 재처리 요청 | 거절, 상태 유지 |

endpoint 중지는 별도 설정이며 delivery를 일괄 삭제하거나 실패 횟수를 증가시키지 않는다. 중지 시점에 이미 시작한 요청은 결과를 기록할 수 있다. late worker가 보내는 결과로 terminal 상태가 역행하지 않게 한다.

## 5. API 동작 초안

이 표는 기능 계약 수준이며 상세 DTO·OpenAPI는 구현 설계에서 만든다.

| 작업 | 제안 경로 | 주요 결과 |
|---|---|---|
| 프로젝트 생성 | POST /api/projects | 201 |
| 프로젝트 조회·수정 | GET /api/projects, PATCH /api/projects/{id} | 200 |
| 키 생성·목록·폐기 | POST/GET /api/projects/{id}/api-keys, POST /api/projects/{id}/api-keys/{keyId}/revoke | 원문 최초 1회, 폐기는 반복해도 폐기 상태 |
| 목적지 등록·조회·수정 | POST/GET /api/projects/{id}/endpoints, PATCH /api/projects/{id}/endpoints/{endpointId} | 201/200, 활성 상태 포함 |
| 이벤트 접수 | POST /v1/events | 신규 202, 같은 내용 중복 200, 충돌 409 |
| 이벤트 목록·상세 | GET /api/projects/{id}/events, GET /api/projects/{id}/events/{eventId} | 페이지 목록·대상 없음 정보 |
| 전달 목록·상세 | GET /api/projects/{id}/deliveries, GET /api/projects/{id}/deliveries/{deliveryId} | 필터·시도·version |
| 재처리 | POST /api/projects/{id}/deliveries/{deliveryId}/replays | 202, 상태·버전·키 충돌 409 |

입력 오류는 400, 인증 실패는 401, 자원 접근 불가는 404, 요청 크기 초과는 413, 프로젝트 데이터 한도는 409 RESOURCE_LIMIT, 저장 장애는 503으로 제안한다. CSRF 검증 실패는 403이다. 오류 응답은 code·message·traceId를 제공하고 내부 스택과 비밀을 포함하지 않는다.

## 6. 인수조건 — Given / When / Then

각 행은 Given(사전 조건), When(동작), Then(기대 결과)으로 구성한다. 현재 모두 미실행이며 문서 검토와 구현 검증은 구분한다.

| ID | Given | When | Then |
|---|---|---|---|
| AC-01 | 사전 생성 사용자, 로그인 전 | 로그인→프로젝트 생성·이름 수정→로그아웃 | 소유 프로젝트가 저장되고 로그아웃 후 관리 요청은 401 |
| AC-02 | 소유자가 다른 두 프로젝트 | 다른 사용자의 자원 조회·수정·키 발급·재처리, 또는 CSRF 검증 없는 상태 변경 | 다른 소유 자원은 404, CSRF 실패는 403, 데이터 변화 없음 |
| AC-03 | 로그인한 소유자 | 키 발급 후 목록·일반 로그 확인 | 최초 응답에만 원문, 이후 비밀 원문 노출 없음 |
| AC-04 | 유효 키와 폐기 키, 기존 대기 delivery | 키로 신규 접수·관리 API 호출 | 유효 키의 접수만 허용, 폐기 키와 관리 인증 용도 거절, 기존 작업 유지 |
| AC-05 | 같은 유형을 구독하는 두 활성 endpoint | 일치 유형 이벤트 접수, 한 endpoint만 실패 | 대상별 delivery가 생성되고 성공한 대상은 재시도되지 않음 |
| AC-06 | 기존 delivery 생성 후 endpoint URL·유형 변경 | 기존 건 처리·재처리와 신규 이벤트 접수 | 기존 URL·연결 고정, 신규 건에만 변경 반영, 화면에 차이 표시 |
| AC-07 | endpoint의 대기·재시도·진행 중 작업 | 중지 후 재개 | 대기 건 전송 보류, 진행 중 호출은 종료 가능, 재개 후 남은 작업 처리 |
| AC-08 | 중지된 endpoint | 새 이벤트 접수 후 endpoint 재개 | 해당 endpoint의 delivery는 생성되지 않고 소급 생성도 없음 |
| AC-09 | 매칭 목적지와 유효 키 | 정상 이벤트 접수 | 저장 완료 후 202, 내부 ID·대상 수 반환, 이후 전달 |
| AC-10 | 이벤트와 delivery 저장 중 오류 주입 | 접수 요청 | 전체 롤백, 성공 응답 없음, 부분 접수 데이터 없음 |

## 7. 구현 전 마지막 설계 항목

제품 동작의 기본값은 POL 표에 모았다. PRD의 OQ-001(외부 배포 범위·비용), OQ-002(서명·키 교체), OQ-003(버전 조합)은 각 작업 직전에 확정한다.

상세 API 스키마, JSON 숫자 비교 방식의 라이브러리 선택, 상태 전이의 DB 원자성, URL 송신 정책 구현, 비밀 보관 방식은 기술 설계에서 정한다. 요구사항의 성공 조건을 만족하는지 별도 구현 검증을 수행해야 한다.
